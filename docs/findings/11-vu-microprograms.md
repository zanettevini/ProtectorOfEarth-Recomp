# 11: VU microprograms inside the ELF

## 1. The question

The master prompt (phase 3) asks to investigate whether the VU0 and VU1
microprograms can be identified and translated statically at build time.

## 2. Short answer

**Yes, and this game makes it easy.** The microprograms are inside the ELF
itself, in a `.vutext` section, and the toolchain left an **overlay table**
saying where each chunk sits in EE RAM and which VU micro-memory address it
goes to.

## 3. How it was found

`readelf -S` showed `.vutext`, `.DVP.ovlystrtab`, `.DVP.ovlytab` and 31
`.DVP.overlay..*` sections. "DVP" is the name the PS2 toolchain uses for the
VU/VIF side. The table layout was deduced from the bytes and checked by the
consistency of the values (s.4); it is implemented in
`tools/analyzer/ps2_elf_audit.py` (`parse_dvp_overlays`).

## 4. What it is

- `.vutext`: 58 KB at `0x0020FAE0`-`0x0021DFD0`, inside the loaded segment.
  This is where the game copies the code to the VU from (by DMA/VIF, `MPG`
  command).
- `.DVP.ovlytab`: 32 entries of 12 bytes:
  - +0x0: offset of the name in `.DVP.ovlystrtab`;
  - +0x4: **LMA**, the address in the EE (all fall inside `.vutext`);
  - +0x8: **VMA**, the destination address in VU micro-memory.
- The 31 `.DVP.overlay..*` sections (outside the loaded segment) have the
  same sizes as the chunks; entries 12 and 22 use the same section, hence 32
  entries for 31 sections.

The entries form **groups** that start at VMA 0 and go up in steps of 0x800
(2 KB per chunk).

Size = distance between the group's LMA and the next group's LMA (the last
one runs to the end of `.vutext`). Wrong turn: the first version of this
table used the sizes of the `.DVP.overlay` sections, which do not match for
the section shared by entries 12 and 22.

| Group | Entries | Highest VMA | Size | Reading |
|---|---|---|---|---|
| A | #00 | 0x0000 | 0x830 (2.0 KB) | fits VU0 (4 KB) or VU1 |
| B | #01 | 0x0000 | 0x260 (0.6 KB) | same |
| C | #02 | 0x0000 | 0x3A0 (0.9 KB) | same |
| D | #03-#10 | 0x3800 | 0x3BB0 (14.9 KB) | **only fits VU1** (16 KB) |
| E | #11-#12 | 0x0800 | 0xD00 (3.3 KB) | fits VU0 or VU1 |
| F | #13-#20 | 0x3800 | 0x3CB0 (15.2 KB) | **VU1 only** |
| G | #21-#22 | 0x0800 | 0xD00 (3.3 KB) | fits VU0 or VU1 |
| H | #23-#28 | 0x2800 | 0x2CC0 (11.2 KB) | **VU1 only** |
| I | #29-#31 | 0x1000 | 0x1798 (5.9 KB) | **VU1 only** |

Conclusion: there are at least four large VU1 programs (D, F, H, I)
(probably renderer variants: skinned/unskinned models, particles, etc.,
**names to be decided**) and five small ones (A, B, C, E, G) that may be VU0
or VU1. The EE has 6 `VCALLMS` ([09](09-executable.md) s.5), so VU0 micro
mode **is used**.

The section names are generated by the toolchain (they contain numbers, not
readable names), so they do not say what each program does.

## 5. What this changes in the plan

- The list of microprograms is **closed and known at build time**: a static
  VU translator (Gitaroo Man's "vu1lift", or our own) can read
  `.DVP.ovlytab`, extract each group from `.vutext` and generate C++. No
  run-time census is needed to discover the programs; a census only serves
  to confirm.
- At run time, when a VIF `MPG` arrives, the uploaded code can be recognised
  by its source address (LMA) or by hash, and tied to the translated
  version. Unknown program = stop with an error (D3).
- Still missing: the VU instruction decoder (64-bit upper/lower pair), flag
  semantics (MAC, status, clipping), the pipeline (`FMAC`, `Q`, `P`
  latencies) and the entry points (addresses the game uses in
  `MSCAL`/`MSCNT`/`VCALLMS`).

## 6. Open

- Confirm each group as VU0 or VU1 (by the DMA channel that sends it: VIF0
  or VIF1).
- List the entry points used by the EE.
- Measure the total number of VU instructions.
